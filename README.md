# crypto_sim — 仮想100万円 暗号資産 自動運用シミュレーション

実際の値動き（yfinance / JPY建て日足）を使い、**架空の100万円**で自動売買を検証する。
実売買・送金は一切行わない。投資助言でもない。

**運用状況（ダッシュボード）: https://men0tai0ko.github.io/crypto_sim/**
GitHub Actionsが30分ごとに自動売買し、この画面に反映する。表示専用で、
この画面自体は売買には一切関与しない。スマホからも見られる。

## GitHub Actions で自動実行する

PCを起動していなくても24時間動かしたい場合、`.github/workflows/trade.yml` が
30分ごとに `live_trade.py --ci` を実行する。

### 手順

1. GitHubにリポジトリを作り、このフォルダを push する
2. Settings → Actions → General → Workflow permissions を
   **Read and write permissions** にする（状態の書き戻しに必要）
3. Actions タブでワークフローを有効化する（初回は手動実行で確認できる）
4. 画面を見たい場合は Settings → Pages で **Branch: data / (root)** を選ぶ
   （`https://<ユーザー名>.github.io/<リポジトリ名>/` で公開される）

### 仕組み

- 実行のたびに `data` ブランチから前回の状態を復元し、1回ぶん売買判断をして書き戻す
- `data` ブランチは毎回**1コミットだけの履歴に強制置換**する。
  追記していくと年に何千コミットも積み上がるため
- 静的ダッシュボード（`publish_static.py` が生成）も同じブランチに置かれる

### ローカル運用との違い

| | ローカル | GitHub Actions |
|---|---|---|
| 稼働 | PC起動中のみ | 24時間 |
| 実行間隔 | 5分（正確） | 30分（**遅延・スキップあり**） |
| ストップ判定 | 5分ごと | 実行時のみ |
| 画面 | 動的・15秒ごと更新 | 静的・実行時のみ更新 |

GitHubのcronは高負荷時に大幅に遅れたり実行が飛ぶことがあり、公式にもそう明記されている。
実際に運用開始直後、最初のスケジュール実行を最後に**2時間まるごと発火しない**状態を
確認した（設定・権限は正常。Actions側の既知の癖で、こちらからは直接解消できない）。
1時間おき1本だと1回飛ぶだけで2時間の空白になるため、`cron: "17,47 * * * *"` として
30分間隔にし、空白の被害を最大1時間に抑えている。

**新規の建て玉判断はもともと1日1回**なので、戦略の中身は変わらない。
影響を受けるのはATRトレーリングストップの判定頻度だけで、
それも「PCが寝ている間はそもそも判定できない」ローカル運用より悪くはならない。

実行が長時間止まっている場合、ダッシュボード上部に警告が出る。
その場合は Actions タブで待機中のジョブが無いか確認し、
無ければ **Run workflow** で手動実行する（書き込み操作のため自動化できない）。

**両方を同時に動かしてはいけない。** 同じ状態を別々に更新して矛盾する。

なお公開リポジトリでは、60日間なにも更新が無いとスケジュールが自動停止する。

### cronの発火漏れを外部から監視する（任意）

上記の通りGitHubのcronは実行が飛ぶことがある。より確実にしたい場合、外部の
無料cronサービス（cron-job.org 等）から `workflow_dispatch` API を定期的に
叩かせることができる。`trade.yml` は既に `workflow_dispatch:` を有効にして
あるので、コード側の変更は不要。**アカウント作成やトークン発行は本人が
行う必要があるため、ここから先は手動セットアップになる：**

1. GitHub の Settings → Developer settings → Fine-grained personal access
   tokens で、**このリポジトリだけ**に絞った、権限は **Actions: Read and write**
   だけのトークンを発行する
2. 好きな外部cronサービスに登録し、30分〜1時間おきに次のリクエストを
   送るよう設定する:
   ```
   POST https://api.github.com/repos/<ユーザー名>/<リポジトリ名>/actions/workflows/trade.yml/dispatches
   Authorization: Bearer <発行したトークン>
   Accept: application/vnd.github+json
   Body: {"ref":"main"}
   ```
3. GitHub側のスケジュールと時間が重なっても構わない。`concurrency: group:
   live-trade` で直列化されるため、同時に2つ動いて状態が壊れることはなく、
   重なった分は無駄になるだけ

### 補助ワークフロー

以下は `trade.yml` とは別に、週次で走る読み取り専用の補助ジョブ。
どちらも `state/` や `data` ブランチには一切書き込まない。

| ワークフロー | 頻度 | 内容 |
|---|---|---|
| `sensitivity.yml` | 毎週月曜 | `python sensitivity.py --check` でパラメータの平坦域が崩れていないか確認。崖を検出したらジョブが失敗する（Actionsタブで気づける） |
| `csv_backup.yml` | 毎週月曜 | `results/live_equity.csv`・`live_trades.csv` を GitHub Releases（固定タグ `csv-backup` を毎週上書き）へバックアップ |

## テスト

```bash
python test_all.py
```

壊れたら困る不変条件だけを検査する（30件）。外部ライブラリ不要、ネットワークにも
本番の `state/` にも触らない（ダッシュボードのCSVダウンロード検証だけは
127.0.0.1のループバックでローカルサーバを一時的に立てる）。主な検査項目:

- 戦略が未来のバーを見られないこと、執行が翌日始値であること
- 手数料・スリッページが正しく引かれ、現金を超えて買わないこと
- ATRトレーリングストップとクールダウンが機能すること
- **実運用とバックテストが同じ設定値・同じプレイブックを使っていること**
- 二重起動のロック判定（生きたPIDは弾き、死んだPIDは無視する）
- Windows で生存確認がプロセスを殺さないこと
- スナップショットの各種指標（レジーム閾値距離・ドローダウン）が正しく、
  データ不足時にNaNをそのままJSONへ書き出さないこと
- `regime.HIGH_VOL` を書き換えたら `classify()` に反映されること
  （デフォルト引数に固定化されて感度検査が効かなくなるバグを防ぐ）
- ダッシュボードのCSVダウンロードが正しいファイル・見出しを返し、
  対象外のパスは404になること
- `build_state()`（`/api/state`）が返す形（キー・型）が壊れていないこと
- 状態ファイルが壊れていても1世代前の `.bak` から復元できること

## リアルタイム仮想運用

過去検証とは別に、**いまの相場に対して架空の100万円を運用し続ける**常駐モードがある。

```bash
python live_trade.py            # 5分間隔で常駐（Ctrl+C で中断、状態は保存される）
python live_trade.py --once     # 1回だけ実行
python live_trade.py --status   # 現状だけ表示
python live_trade.py --reset    # 元手100万円から仕切り直す
```

`run_live.bat` をダブルクリックしても起動する。PC起動時に自動で走らせたい場合は、
`Win+R` → `shell:startup` で開くフォルダに `run_live.bat` のショートカットを置く。

1ループでやっていること:

1. 現在値を取得（5分足の最新・全銘柄まとめて1リクエスト）
2. **相場付きを判定して戦略を切り替える**（`regime.py`）
3. 保有中の銘柄は **ATRトレーリングストップを毎ループ判定** — 日足シグナルを待たずに損切りが効く
4. 新規の建て玉判断は1日1回（日足が確定する単位）
5. 目標ウェイトへリバランスし、状態とログを保存

| 相場付き | 判定 | 使う戦略 | エクスポージャー上限 |
|---|---|---|---|
| 強気 | BTCが200日線の上・ボラ落ち着き・上昇銘柄が半数以上 | 分散保有（50日線超えの銘柄を均等） | 100% |
| 中立 | BTCは200日線の上だが、荒れている or 銘柄がついてこない | ドンチャン20/10 | 60% |
| 弱気 | BTCが200日線の下 | ドンチャン55/20 + ATRストップ | 40% |

**同時に2つ起動してはいけない。** 同じ状態ファイルを奪い合って売買が矛盾する。
`state/live.lock` の心拍で二重起動は自動的に弾かれる（`--status` は影響を受けない）。
PCの強制終了でロックが残っても、心拍が古ければ次回起動時に無視される。

1銘柄あたりの上限は **30%**（`regime.MAX_WEIGHT`）。実運用とバックテストが同じ値を
同じ場所から読むので、片方だけ変わって「検証したものと違うものが動いている」状態にならない。
状態は `state/live_state.json`、
履歴は `results/live_trades.csv` と `results/live_equity.csv`。
PCを落としている間は止まり、再開すると現在値からそのまま続行する。

### シャドー判定（記録専用・実売買には一切影響しない）

1日1回の建て玉判断のたびに、ボラ閾値だけ変えた（`HIGH_VOL=0.90` → `0.75`。
`sensitivity.py` で「0.75以上は安定」と確認済みの値）別のレジーム判定も
あわせて行い、実際の判定と一致したかどうかだけを `results/shadow_regime.csv`
に記録する。`self.targets` / `self.broker` のどちらにも渡さないため、
建て玉にも損益にも一切影響しない。

目的は、パラメータを見直す材料を「両期間の結果を見てから判断する」という
過剰最適化を防ぐルールに沿った形で安全に貯めること。ここで記録した差分だけを
根拠に実運用の閾値を今すぐ動かすことはしない。

## ブラウザで運用状況を見る

```bash
python dashboard.py --open      # http://127.0.0.1:8787 を既定のブラウザで開く
python dashboard.py --port 9000
```

`run_dashboard.bat` をダブルクリックでも起動する。表示されるもの:

- 稼働中／停止中のバッジ（ロックの心拍とPIDの実在で判定）。favicon の色も連動
- 総資産・損益・現金・評価額・建玉率・ピーク比。**タブのタイトルにも総資産と損益**を出すので、
  タブを切り替えなくても状況が分かる。**建玉率には推移のミニグラフ**を添えて、
  上限まで攻めていた時期が一目でわかるようにしてある
- いまのレジームと選択中の戦略、その判断根拠。**判定を構成する3条件
  （200日線比・ボラティリティ・上昇銘柄比率）が、切り替わる閾値までどれだけ
  離れているか**を監視ユニバースと同じバーで表示するので、相場付きが
  変わる予兆に気づける
- **監視ユニバース** — 全銘柄の30日スパークライン・現在値・前日比・移動平均比、
  そして「シグナル点灯まであと何%」をバーで表示。基準は現在の戦略に連動して切り替わる
- 資産推移チャート（**24時間 / 7日 / 30日 / 全期間**の切替、ホバーで詳細）。
  グラフ下の**レジーム帯**で、そのとき何を選んでいたかが分かる（曲線の形の理由が読める）。
  表示は**「総資産」（折れ線）／「増減」（記録間隔ごとの差分を増加/減少で色分けした棒）／
  「ドローダウン」（そのときの最高値から何%下げているか）**の3つを切り替えられる。
  ドローダウンは間引き前の全履歴からピークを追っているので、画面上の期間フィルタで
  絞り込んでも見落としが出ない
- **期間サマリー** — 直近7日／直近30日の損益をひと目で見られるカード。
  運用開始からまだ日が浅くその期間ぶんのデータが無い場合は「運用開始から」の値になる
- **資産の内訳** — 現金を含めた全体の構成を積み上げバーで表示。
  銘柄の色は固定で、並びも常に同じ順（保有が入れ替わっても隣り合う色の組が変わらない）
- 保有ポジション（現在値・**ストップ価格**・含み損益・構成比）。
  **「ストップまでの距離」もバーで表示**（監視ユニバースの「点灯まで」と同じ部品だが、
  近いほど良いバーとは意味が逆なので、近づくほど警戒色に変わる）
- 取引成績 — 累計実現損益・決済回数・勝率・平均利益／損失・PF・最大益／最大損。
  **銘柄別に実現損益と含み損益を並べた表**も出す（どの通貨で勝てているかは合計では見えない）。
  **保有期間の分布**（0〜1日／2〜5日／6〜10日／11〜20日／21日以上）も表示し、
  ホイップソー（往復売買）の傾向に気づけるようにしてある
- 売買履歴。**資産推移／売買履歴はそれぞれCSVでダウンロードできる**
  （運用中の `results/` はGit管理外のため、手元に残したい場合はこれまで手動で
  ファイルを探しに行く必要があった）
- **直近のエラー** — 通信断などの記録に加え、**直近14日の発生件数を日ごとの棒で表示**。
  1〜2回のノイズと、頻度そのものが増えている劣化の兆候を見分けやすくする
- **日足データの欠損警告** — 欠けている日付に加えて、自動での取り直し（1時間おき）を
  すでに試みたかどうかも表示する。試みてもなお埋まっていない場合は、
  配信元側の欠測である可能性が高いと分かる

更新まわり:

- **15秒ごとに自動更新**。経過秒数を常時表示し、「今すぐ更新」ボタンで即時取得もできる
- **トレーダーの次の売買判断までのカウントダウン**を表示（画面は15秒ごとでも中身は5分に1度しか変わらないため）
- **タブが非表示の間はポーリングを停止**し、戻ると即座に最新化する
- トレーダーが起動しているのにスナップショットが更新されていない場合は**警告を出す**。
  「プロセスは生きているのにデータが古い」が最も気づきにくい壊れ方のため
- 資産ログは更新時刻とサイズが変わったときだけ読み直す（1年分7.8MBでも再読込は1回あたり1ms未満）

設計上、**トレーダーとは別プロセス**にしてある。組み込みにすると
トレーダーが落ちた瞬間に確認手段も消えるため、「止まっていること」を
確認できなくなる。表示するのはトレーダーが書いたファイルだけなので、
この画面が価格を取りにいくことはない。

待ち受けは `127.0.0.1` のみ。LANや外部からは見えない。

**停止条件**: 総資産が0円以下になったら終了する。ただし現物のみ・ショートなしのため、
保有4銘柄すべてが無価値にならない限り0円には到達しない。実質的な撤退ラインを設けたい
場合は `--stop-below 500000` のように明示する。

## バージョン管理

リポジトリはこの `crypto_sim/` を起点にしている（1つ上の日経Sim側とは独立）。

追跡するのは**コードとドキュメントだけ**。次のものは `.gitignore` で除外している。

| 除外するもの | 理由 |
|---|---|
| `cache/` | 価格データ。`python data.py` で取り直せる |
| `results/` | 検証結果・図・稼働ログ。コードから再生成できる |
| `state/` | 運用中の状態。**5分ごとに書き換わる**ため差分がノイズになる |

運用中の資産推移を残したい場合、`results/live_equity.csv` は Git ではなく
別途バックアップすること（追記のたびにコミットが必要になり履歴が読めなくなる）。

`.gitattributes` で改行コードを固定してある（`.bat` のみ CRLF）。

## 前提条件

- **ユニバース**: BTC-JPY / ETH-JPY / XRP-JPY / SOL-JPY（JPY建て直接なので為替換算不要）
- **時間軸**: 日足
- **コスト**: 手数料 0.15%（取引所テイカー相当）＋ スリッページ 0.10%
  販売所のスプレッド（往復2〜4%）は使わない前提。使うと短期戦略はまず成立しない
- **現物のみ**（ショート・レバレッジなし）
- **執行**: i日目の**終値まで**を見て決めた注文を、**i+1日目の始値**で約定
  → 終値判定・終値約定にすると未来を覗くことになり（look-ahead bias）、成績が全部嘘になる
- **ストップは終値判定**。日中の値動きは追えないので、実際より逃げ遅れる側に見積もっている
- データは Yahoo の JPY建て。実質「USD建て×為替」の合成に近く、国内取引所の板とは乖離する

## 検証結果（2026-08時点）

`python backtest.py --split` の要旨。**全戦略が検証用期間ではBTC買い持ちに勝ち、
検証外期間では全戦略が負けた。**

| 戦略 | 2018-2022 リターン / 最大DD | 2023-2026 リターン / 最大DD |
|---|---|---|
| BTC買い持ち | +41% / **-81.5%** | **+349%** / -49.4% |
| 均等分散(月次) | +163% / -88.0% | +424% / -61.2% |
| ドンチャン20/10 | +207% / **-29.8%** | +30% / **-29.8%** |
| ドンチャン55/20 | +163% / **-14.9%** | +57% / **-16.7%** |

## 実運用戦略（レジーム切替）の検証

`strategies/regime_switch.py` は live_trade.py と同じ判断を過去データで再現する。
`python backtest.py --split` で他の戦略と並べて比較できる。

| 期間 | リターン | 最大DD | Calmar | Sharpe | BTC買い持ち比 |
|---|---:|---:|---:|---:|---:|
| 2018-2022 | +1248% | **-26.5%** | **2.57** | 1.54 | +1207pt |
| 2023-2026 | +247% | **-26.2%** | **1.58** | 1.25 | -114pt |

**両期間ともCalmar（年率÷最大DD）が全戦略中で最も高い。** そして
**最大DDが両期間とも -26% 台で揃っている** — リターンは相場任せでも、
落ち込みの深さは設計で決められる、という当初の結論がそのまま出ている
（買い持ちは -81.5% と -49.4% で倍近くぶれる）。

上昇相場では買い持ちに負ける（-114pt）。これは現金を持つ以上避けられない。

### クールダウン（ストップ後の再エントリー禁止）

売買ログを調べたところ、**買い直しの22.9%が売却の翌日以内**に起きていた。
トレーリングストップに引っかかった直後の銘柄を即座に買い戻すのは、
崩れ始めた動きに乗り直す行為で、往復売買になりやすい。

`regime.COOLDOWN_DAYS = 10` で10日間の再エントリー禁止を入れた結果:

| | クールダウン無し | **10日** |
|---|---|---|
| 2018-2022 年率 / 最大DD / Calmar | 60.8% / -31.4% / 1.93 | **68.2% / -26.5% / 2.57** |
| 2023-2026 年率 / 最大DD / Calmar | 39.7% / -31.4% / 1.26 | **41.4% / -26.2% / 1.58** |

**両期間・リターンとドローダウンの両方が同時に改善する。** 7〜20日が広い平坦域を
作っており（Calmar は検証用期間で 1.38〜1.71）、特定の値だけが跳ねる偶然ではない。
6日以下・25日以上では崩れる。平坦域の中央として10日を採用した。

ただしこれも**両期間の結果を見たあとに探して見つけたもの**である点は変わらない。

### 重大な但し書き

**この戦略のレジーム判定ルールは、両期間の結果を見たあとに設計している。**
つまり 2023-2026 は本当の意味での検証外期間ではない。上の数字は「過去に当てはめたら
こうなった」以上のものではなく、将来の再現性を保証しない。

2.5倍と3.0倍の取引ログを実際に突き合わせたところ、最初に分岐するのは
2023-11-21のXRP-JPYの手仕舞い（ストップが早い2.5倍はここで利確、
3.0倍は翌日まで保有して悪い価格で手仕舞い）。この1トレードだけを見ると
3.0倍側が悪化しているが、**期間全体の銘柄別実現損益ではETH-JPY
（134,023円→471,709円）とSOL-JPY（496,371円→906,467円）が大きく
改善しており**、ストップを緩めたことで2023-2026の強いトレンドを
早期に振り落とされず乗り続けられたことが、全体の改善の主因と分かった。
1トレードの偶然ではなく、複数銘柄にまたがる一貫した効果であり、
**過剰最適化のサインではなく妥当な挙動**と判断する。

とはいえ、3.3付近が頂点でそこから緩やかに下がっていく形（現在値3.0は
坂の途中で、ピークではない）であることも分かった。**この結果だけを
根拠に3.0→3.3のような微調整はしない**（過剰最適化を防ぐルール通り、
値を1つずらして崩れないことを確認しただけでは採用の理由にならない。
別の検証期間でも同じ坂の形が出るかを確認してから判断する）。

`sensitivity.yml` が毎週この確認を自動で行う（`--check` オプション）。
自動判定の対象は大局トレンドの移動平均とATRストップ幅の2つ
（ボラ閾値・1銘柄上限は意図した段差を持ちうるため対象外。
「過剰最適化を防ぐためのルール」の節参照）。

## 過剰最適化を防ぐためのルール

- 作り込みは 2018-2022 の期間だけで行う。2023- は検証にしか使わない
- パラメータを1つずらして崩れる結果は偶然とみなす
- 手数料・スリッページを外した数字は見ない
- 取引回数が極端に多い戦略は、コストを上げて再確認する
